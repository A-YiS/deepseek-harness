# Agent Note: 桌面端后端目标

Status: implemented

[English](2026-10-08-desktop-backend-target.md) | 中文

## 问题

打包窗口从 `dsh-app://app` 提供页面，并把其余请求全部转发给外壳自己拉起的 Host 进程，因此每个会话都属于本机。要使用另一台 Harness，只能在应用内嵌浏览器里加载那台 Harness 自己的前端：远端构建会顶替打包 UI，外壳的界面、更新流程与原生面随之失效。让打包 UI 直接驱动远端 Host，需要在不额外发布一个客户端的前提下更换上游。

## 决策

外壳只维护一个活动后端目标——它拉起的 Host，或产品页通过 `dshDesktop.backend` 接上的远端 Host。一个目标携带应用源站本就依赖的三个值：上游 origin、该 authority 承认的会话 Cookie、以及那台 Host 自己的 index 会渲染的启动注入表。`protocol.handle`、WebSocket 凭据改写与启动 IPC 全部读活动目标；接入与离开都重载文档，于是启动注入、插件行、上游 origin 与流基础地址一起变化，页面只在启动时读一次。

`backend.connect` 接受产品页给出的回环 origin，并在主进程内完成 Cookie 交换与启动接管，凭据因此从不进入文档。`backend.status` 之所以存在，是因为注入的产品图属于活动 Host，无法描述外壳自己选了谁。远端目标必须是回环：会话 Cookie 绑定其 authority，WebSocket 凭据改写接受同一组回环 authority。Host 版本只比较并作为警告上报，而不是否决——兼容面是启动图与应用层 Remote API，版本号决定不了它们。

## 备选方案

- **在本地 Host 内部代理全部路由。** 本地 Host 拥有自己的启动注入表，无法被要求渲染另一台 Host 的行，客户端会因此启动两张模块图。
- **让远端 Host 充当外壳的 Host 进程。** 外壳与 Host 之间的私有 Node IPC 承载启动注入、退出检查与更新任务；改成远端进程就要先把这些都搬到线上。
- **在内嵌浏览器标签页里加载远端前端。** 这是改动前的行为，也正是改动的原因：它顶替桌面 UI，而不是驱动它。

## 影响

- 远端 Host 提供客户端插件行，因此窗口渲染那台 Host 的插件、同时保留打包外壳；本地独有的客户端插件在把本地控制面绕开远端之前不会出现。
- 被拉起的本地 Host 继续运行，因为承载隧道的插件在它里面；远端接入期间本地 Agent 由插件暂停，而不是由外壳暂停。
- 指向本机路径的原生面（目录选择器、拖入文件的路径引用）仍然描述这台机器，需要各自的远端方案。
